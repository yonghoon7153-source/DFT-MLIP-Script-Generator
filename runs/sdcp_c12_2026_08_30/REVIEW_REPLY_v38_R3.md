  `_hosts_all.txt` · `_probe_*.out`. 증거 `PLACEMENT_PROBE.json` 과 규칙 `_place_flags.sh` 는 남깁니다.
  남의 lock 이면 어느 파일도 건드리지 않습니다.

## P1-2 — 허용 환경을 검증 범위로 좁혔다 ✅ (한계 명시)

### 메모리 — 실행 노드마다 봅니다
프로브 페이로드를 `hostname` → **`/bin/sh <root>/_probe_node.sh`** 로 바꿨습니다. 각 랭크가 **자기
노드**에서 `/proc/self/cgroup` 경로를 리프→루트로 걸어 최소 제한과 `MemTotal` 을 읽어
`host \t limit \t memtotal` 로 보냅니다(POSIX sh, 외부 의존 없음). 판정기는 프로브마다 실행 노드
**각각**에 `노드당 필요량 ≤ 노드 메모리 × usable_frac` 을 적용하고, 노드별 값을
`PLACEMENT_PROBE.json` 에 기록합니다.

지적하신 구성(러너 188 GiB · 실행 노드 64 GiB)이 이제 갈립니다. v39 실물 시연:

| | 조건 | 결과 |
|---|---|---|
| D | 48노드×2동시 · 96호스트 · 실행 노드 15.7 GiB | 프로브 2개 동시 통과 · 서로소 · **실행 노드 메모리 최소 15.7 GiB ≥ 필요 6.1/0.85** |
| F | 같은 조건, **실행 노드 MemTotal 4 GiB** (러너 호스트는 15.7) | `48 노드(node01…node48): 노드당 필요 6.1 GiB > 가용 4.0×0.85=3.4 GiB` → **첫 VASP 전 정지** |

e2e 음성도 넣었습니다 (실행 노드 1 GiB → rc 2). 96 노드가 같은 사유면 96 줄이 아니라 한 줄로 접습니다.

### wrapper — 이 제출 경로에서 제외했습니다
지적대로 wrapper 는 슬롯을 점유·반납하지 않아 장시간 서로소를 이 러너가 보장할 수 없습니다.
`run_staged`·`run_job` **둘 다** 거부하고(시연 H), README 의 kinds 목록에서 뺐습니다
(`mpirun|mpiexec|srun` · `none` 은 스모크용으로만 표기). 쓸 일이 생기면 별도 계약으로 다시 엽니다.

### 함께
- `SLURM_MEM_PER_CPU × SLURM_CPUS_ON_NODE` 도 관측에 넣었습니다.
- 문서 문구를 정확히 했습니다: *"러너 호스트에서 SLURM·cgroup 계층·/proc/meminfo 의 최소를 먼저 보고,
  배치 프로브가 **실행 노드 전부**에서 같은 값을 읽어 노드마다 다시 판정합니다."* — "작업 제한까지
  확인했다" 는 표현은 이 범위 안에서만 씁니다.

### ⚠ 남은 한계 (지적하신 것 포함)
- cgroup 마운트 경로는 `/sys/fs/cgroup`(v2) · `/sys/fs/cgroup/memory`(v1) 고정입니다. cgroup namespace
  안에서 경로가 다르게 보이는 환경은 프로브가 제한을 `none` 으로 보고할 수 있고, 그때 판정기는
  **"제한을 못 읽었다" 로 멈춥니다**(통과시키지 않습니다). 이번 인수처(Slurm · 통상 마운트)에서
  확인하는 것으로 범위를 잡았고, 이식성 전체는 승인 조건으로 넓히지 않았습니다.
- 프로브는 `hostname`+메모리 읽기 프로세스의 배치이고 VASP 자체의 배치는 아닙니다 — 같은
  launcher·같은 플래그라 같을 것으로 기대하며, 그 기대를 JSON 의 `⛔_이_기록이_보증하지_않는_것` 에 적었습니다.
- srun step 자원 정책(`--exclusive` 등)은 현장 설정에 달려 단정하지 않습니다.
