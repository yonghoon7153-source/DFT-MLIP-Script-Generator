## 0. 이번 판의 성격 — 물리는 안 바뀌었다

v36 → v37 에서 **INCAR·POSCAR·k·자세·사전등록은 한 글자도 안 바뀌었다.**
바뀐 것은 (a) 실행 배치 계약, (b) 그것을 강제하는 러너 검사, (c) 문서다.
따라서 이 리뷰는 **"맞는 양을 재고 있나"가 아니라 "이 계약이 실제로 지켜지게
돼 있나"** 를 봐 달라는 것이다. 다만 §5 에 물리 쪽 자문 1건을 따로 올린다.

## 1. 왜 생겼나 — 2026-09-04 실패

인수처(48코어/노드 · 188 GB + swap 32 GB)에서 **슬랩 잡이 전부 OOM** 났다.
분자 잡은 살아남았다. 인수처 회신: "이전 게 빡빡하게 돌아갔는데 이번에 살짝
넘쳐서 터진 듯", "노드 1개당 1개잡 돌렸다", "그 슬랩잡이 죽은 거예요, 무거운 거".

우리 모형으로 역산하면:

| | floor | + 48랭크 × 0.9 | 계 | 가용 188×0.85 = 159.8 |
|---|---|---|---|---|
| 슬랩 최악 (224원자) | 119.4 | 43.2 | **162.6** | ⛔ 2.8 GB 초과 |
| 분자 (35원자) | 12.9 | 43.2 | **56.1** | ✔ 35 % |

**두 부류를 정확히 가른다.** 여기서 모형 오차 f 의 범위도 나온다 —
슬랩이 죽었으므로 f·162.6 > 159.8 → f > 0.98, 분자가 살았으므로
f·56.1 < 159.8 → f < 2.85. ⇒ **0.98 < f < 2.85**.

⚠ 부수적으로 발견: 48랭크로 돌리면 최장 잡이 31.3 h × 3.73 = 117 h 라
요청 walltime 84 h 에 **잘린다**. "몇 번 돌아가다 멈췄다"가 이것일 수도 있다
(확증 못 함 — 로그를 못 받았다).

## 2. 처방 — INCAR 을 안 건드린다

랭크 192 는 그대로 두고 **노드에 펼친다**.

|---|---|---|---|---|
| 1 (인수처가 한 것) | 48 | 162.6 | 102 % | ⛔ 0.98 |

## 3. 코드 — 무엇을 넣었나

### 3.1 `run_staged.sh` 메모리 사전검사
- 위치: 랭크 배수 검사 **뒤**, `PP=${PP:?}` 와 첫 VASP 실행 **앞**.
- 입력: `NODE_MEM_GB` → `SLURM_MEM_PER_NODE` → `/proc/meminfo` 순으로 노드 메모리,
  `VASP_NODES` → `SLURM_JOB_NUM_NODES ÷ JOBS_PARALLEL` 순으로 노드/잡.
- 판정: `(floor + 랭크×repl) ÷ 노드수 × 노드당동시잡 ≤ 노드메모리 × usable_frac`.
  넘으면 `exit 2` + 필요한 노드 수를 계산해 출력.
- **값을 못 알아내면 멈춘다.** 탈출구는 `MEM_GUARD=off` 하나뿐이고 껐다고 크게 찍는다.
- 통과해도 여유 < 안전계수면 **경고**한다(막지 않는다).
- `NPAR` 계산을 가드 앞으로 올리고 뒤 사본을 삭제했다.

실측 (v37 실물):
```
VASP_NODES=1 → ⛔ 183 % — 이대로 돌리면 OOM 입니다.        [exit 2]
VASP_NODES=2 → ✔ 91 % 통과 + ⚠ 여유 1.09배가 안전계수 2.0배보다 얇다
VASP_NODES=4 → ✔ 46 % 통과 (모형이 2.19배 틀려도 견딥니다)
값 미상        → ⛔ 필요한 값을 알아내지 못했습니다              [exit 2]
SLURM 16노드   → 할당 16 ÷ 동시 4 = 4노드 자동 유도 → 46 % 통과
```

## 5. ★ 우리가 스스로 못 미더운 것 (여기를 봐 주십시오)

### P0 후보 — MLIP 가 sdcp 흡착 **부호**를 틀릴 가능성
자세 선정은 UMA 로 했다(`prospective_basins_2026_08_29.json`, DFT 보기 전 동결).
그런데 `E_pose` 를 보면:
- `ptfe_c10` b00 = **−0.2660 eV** (붙는다)
- `sdcp_neutral` b00 = **+0.0200 eV** — 101 basin **전부 양수**. UMA 는 SDCP 가
  이 슬랩에 **흡착하지 않는다**고 말한다.

그런데 wave1 **DFT** 는 같은 조각·같은 슬랩에서 `E_ads ≈ −0.77 eV` 였다
(`db/properties/sdcp_wave1_job_energies_2026_08_28.csv`). **부호가 반대이고 0.79 eV 차이다.**
⇒ 선정에 쓴 모델이 이 조각에서 부호를 틀린다면 **basin 순위(b00 이 최소)도 못 믿는다.**
사전등록·동결 규율은 지켰고(먼저 고르고 나중에 본다) 이 불일치를 재는 것이 이
캠페인의 목적이기도 하지만, **b00 을 "primary" 라고 부르는 것이 정당한지**를
봐 주십시오. 우리는 사후 교체를 하지 않을 생각이다.

### P1 후보 — stress 자세 선택이 에너지로 결정되지 않는다
b12(0.2976) · b13 Ni_top(0.3006) · b15 Li_top(0.3053) 이 **8 meV 안에** 몰려 있다.
b12 가 뽑힌 사유는 에너지가 아니라 **"앵커 원소가 primary(H)와 다르다(O)"** 는
사전 규칙이다. 규칙은 방어되지만 "b13 이 아니라 b12" 는 에너지가 정한 것이 아니다.
이 상태에서 stress 결과를 어떻게 서술해야 하는지 문구를 봐 주십시오.

### P1 후보 — 진공 검사가 면내를 안 본다
`emit_struct` 의 진공 보고가 **"c 를 넘는 이미지만"** 본다. 면내 자기이미지는
검사 대상이 아니었다. 이번에 손으로 재보니 전 잡 4.6~6.1 Å 로 통과지만
(ptfe b00 5.65 · sdcp b12 4.61), **검사에 구멍이 있는 것은 맞다.**
특히 C10F22 는 b축 span 이 셀의 **1.033배**라 셀보다 길다.

### P1 후보 — 배포 그림에서 원자가 조용히 사라졌다 (이번에 잡혔다)
`.vesta` 의 `BOUND` 가 `0 1 0 1 0 1` 로 **하드코딩**돼 있었다. 파일에는 있는데
화면에서 사라지는 fail-open 이다. 1저자가 C10F22 를 열어 CF3 가 없는 것을 보고
제보해 발견했다. 두 단계로 고쳤다:
① BOUND 를 실제 분율 범위에서 계산(넘칠 때만 넓힌다 — 안 넘치는 축까지 넓히면
   슬랩이 한 겹 더 타일링돼 가장자리에 여분 줄이 생긴다).
② 그래도 안 됐다 — **VESTA 는 좌표를 [0,1) 로 접는다.** C10F22 는 b 축 분율 span 이
   1.033 이라 어떤 평행이동으로도 3.3 % 는 넘어간다(실측: 편 좌표 1조각 → 접은 좌표
   4조각). ⇒ `--vesta_super 1 2 1` 로 **표시용 슈퍼셀**(슬랩만 타일링·분자 하나)을
   도입. 검증: 접은 뒤 조각 수 4 → **1**.
**봐 주실 것**: 표시용 슈퍼셀에서 분자를 하나만 남기는 것은 표시 선택이다. 파일
제목·README 에 "계산 셀은 이것의 b 절반이고 셀마다 분자가 하나" 라고 적었는데,
이 정도로 오독(피복률로 읽기)이 막히는지.

### P2 — 모형의 한계 (우리 표기)
`memory_model` 은 **실측이 아니다**. `⛔_실측_아님` 필드에 "통과는 안전 보증이
아니라 명백한 불가를 시작 전에 거른 것" 이라고 박아 두었다. 이 표현이 충분한지.
